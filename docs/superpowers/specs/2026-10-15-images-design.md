# Images in notes: design

Status: approved; implemented per docs/superpowers/plans/2026-10-15-images.md.

## Goal

A note can show images. The user pastes or drops an image into the editor; the browser encrypts it with the vault key and uploads only ciphertext. The note body holds `![alt](inked://<imageId>)`. The renderer fetches, decrypts and shows it. The AI can add images through the MCP.

The server stays zero-knowledge: it stores an opaque blob and never sees pixels, type, dimensions or which note uses it.

## Decisions

- **Encrypted in the browser.** Same key hierarchy as notes. No plaintext image ever reaches the server.
- **No public links.** `![](https://…)` does not load anything. The CSP does not change (`img-src 'self' data: blob:`). A public `<img>` or `<video>` would send each viewer's IP and referrer to a third party, and widening `img-src` weakens the CSP for every user of the instance.
- **Paste and drop only in the browser.** A URL is only an address. Fetching it needs a cross-origin request that `connect-src 'self'` and missing CORS headers both block, or a server relay (rejected: the server would see the URL and gain an SSRF surface). Pasted or dropped bytes are already in the browser.
- **The MCP may fetch.** It runs on the user's machine under the user's granted permissions, fetches and encrypts locally, and uploads through the same server route as the browser. The server needs no fetch endpoint.
- **Images only in v1.** No video, no SVG.

## Section 1: storage, encryption, API

### Table

```
images(
  id         TEXT PRIMARY KEY,                                  -- UUIDv4, generated by the client
  vault_id   TEXT NOT NULL REFERENCES vaults(id) ON DELETE CASCADE,
  size       INTEGER NOT NULL,                                  -- bytes of enc_blob
  enc_blob   BLOB NOT NULL,
  created_at TEXT NOT NULL
)
INDEX images_vault ON images(vault_id)
```

Added to the `SCHEMA` string in `server/src/db.ts` (`CREATE TABLE IF NOT EXISTS`, so existing databases gain it on boot).

### Format

`enc_blob = iv[12] || ciphertext||tag`, raw bytes (not base64, unlike text fields: 33% smaller). AES-256-GCM with the `vaultKey`, fresh random IV. AAD (UTF-8) is `inked/image/{vaultId}/{imageId}`, so a blob cannot be moved to another slot. Plaintext is the raw image bytes. This adds one row to the ciphertext table in `docs/architecture.md`.

The type is not stored. After decrypt the client sniffs magic bytes and accepts png, jpeg, gif and webp only.

### Routes

Ownership is checked as for notes (`ownedVault`; vaults are owned by one user, and a missing or foreign vault is a 404). Writes need the session cookie and `X-Inked: 1`, like every non-GET.

- `POST /api/vaults/:vaultId/images/:imageId`: body is `application/octet-stream`.
  - Fastify gets an `application/octet-stream` content-type parser (`parseAs: 'buffer'`) and a per-route `bodyLimit` of 10 MiB. The global JSON `BODY_LIMIT` is unchanged.
  - 415 if the content type is not octet-stream. 400 if the body is under 29 bytes (iv 12 + tag 16 + 1 byte). 413 over 10 MiB. 409 if the id exists. 413 with a quota message if the user's total would exceed the quota. 404 for an unknown or foreign vault. `:imageId` must be a UUID, else 400.
  - Returns 201 `{ id, size, createdAt }`.
- `GET /api/vaults/:vaultId/images/:imageId`: returns the blob as `application/octet-stream` with `X-Content-Type-Options: nosniff`. 404 if absent or the vault is not the user's.
  - The global `onSend` hook sets `cache-control: no-store` on every `/api` path. This route needs `Cache-Control: private, max-age=31536000, immutable` (an id's content never changes), so the hook must leave a cache-control that the route already set. A test pins this.
- No `DELETE` in v1.

### Quota

`INKED_IMAGE_QUOTA_MB`, default 1024, read in `server/src/config.ts`. The check is `SUM(size)` over the images in the user's vaults plus the new blob.

### What the server learns

Image count, sizes and upload times per vault. Not type, dimensions, or which notes reference an image. Added to the threat-model paragraph.

### Orphans

References are inside encrypted bodies, so the server cannot know what is unused. Deleting a vault cascades. A client-side "Remove unused images" action (scan decrypted notes, delete unreferenced blobs) is a follow-up and needs a `DELETE` route then.

## Section 2: MCP tool

New tool `add_image`, new policy action `image.create` (`mcp/src/policy.ts`, `mcp/src/tools.ts`, `mcp/src/ops.ts`). Not granted by default. As with every tool, it is not registered unless the config allows it.

Input: `vault`, plus exactly one of `url` (https) or `path` (local file), and optional `alt`.

Flow, all local:

1. Get the bytes (fetch or file read), enforcing the 10 MiB cap while streaming.
2. Sniff magic bytes; accept png, jpeg, gif, webp only.
3. Encrypt with the vault key (same format and AAD as the browser) and `POST` it to the same route.
4. Return `![alt](inked://id)`. The AI then writes it into a note with `create_note`, `append_to_note` or `update_note`.

The fetch runs on the user's machine, so it needs its own guards:

- **URL:** `https:` only. Resolve DNS and refuse loopback, private, link-local and other reserved ranges (IPv4 and IPv6). Connect to the resolved address, not the name (defeats DNS rebinding). Re-validate every redirect hop, at most 3 hops. Timeout, and abort past the size cap.
- **Path:** refused unless it resolves (after symlink resolution) inside a folder listed in a new config key `imageDirs` (default empty, so `path` is off until the user opts in). Non-image bytes are refused regardless.
- **Audit:** the local audit log records the vault id and the image id only, matching the log's ids-only rule. The URL, the path and the bytes are never logged.
- `docs/mcp.md` states that the URL is requested from the user's IP and that the model provider sees the returned token only.

## Section 3: renderer and editor (web)

### Rendering

`renderMarkdown` stays a sync Markdown-to-HTML step; decryption is async, so it is two steps.

1. In `web/src/markdown/render.ts`, markdown-it still emits `<img>`. A DOMPurify `afterSanitizeAttributes` hook handles every `<img>`:
   - `src` matching `^inked://<uuid>$` becomes `data-inked-image="<uuid>"` with `src` removed.
   - Any other `<img>` is replaced by a plain external link (`target=_blank`, `rel=noopener noreferrer`) showing its alt text, falling back to the URL. Nothing external loads. `javascript:` and `data:` sources are dropped.
   - markdown-it's `validateLink` already rejects `javascript:`; the `inked:` scheme passes it, and a test pins that.
2. The note view (`NotePane`, and `NodePreview`, which shares the renderer) scans `img[data-inked-image]` after each render and resolves each through an `ImageStore`.

### ImageStore (web/src/state)

- `get(vaultId, imageId)`: cache hit, else `GET`, decrypt with the vault key, sniff the type, make a `blob:` URL. Concurrent calls for one id share one request.
- `put(vaultId, imageId, bytes)`: used by paste so the preview needs no re-download.
- The cache lives in memory only, with blob URLs. On lock or logout, revoke every URL and clear the cache. Nothing goes to localStorage, sessionStorage or IndexedDB (same rule as keys).
- Loading shows a skeleton. Any failure (404, decrypt failure, unsupported type) shows an inline "Image unavailable" box and never breaks the rest of the note.
- `renderUntrustedMarkdown` (Ask answers) already turns images into alt text and does not change.

### Editor

The editor is a `<textarea>` in `NotePane` (logic in `useNoteEditor`).

- `onPaste`: if `clipboardData.files` holds an image, `preventDefault()`, generate the id, insert `![](inked://id)` at the caret at once, then encrypt and upload in the background. `ImageStore.put` caches the bytes. Pasted text and URLs behave exactly as before.
- `onDrop`: image files dropped on the textarea go through the same path.
- Rejected pastes (type not allowed, over 10 MiB, request refused) show a toast and insert nothing. If the upload fails after the token is inserted, the token is removed and a toast shown.
- The body is still plain Markdown, so the save queue is unchanged. A paste into a not-yet-saved note works because images belong to the vault, not the note.

### Search, semantic index and Ask

The chunker and the search text builder must not feed `inked://<uuid>` to fuzzy search or the embedder. They keep the alt text and drop the target. The plan locates these (`core/src/search`, `core/src/semantic`, `core/src/rag`) and adds tests.

## Section 4: limits, errors, tests, docs

### Limits

10 MiB per image; quota per user (Section 1); the existing 7-day session model applies. The existing rate limiter only counts login failures, so the quota is the write cap.

### Tests

- **core:** encrypt/decrypt round trip; wrong vault id or image id in the AAD fails.
- **server:** auth required; foreign vault is 404; 415, 400, 413, 409; quota; cascade on vault delete; `nosniff` and the immutable `cache-control` on GET; `no-store` still applies to other `/api` routes.
- **web:**
  - Renderer: `inked://` becomes `data-inked-image`, external `<img>` becomes a link, `javascript:` and `data:` are stripped, no `src` remains on a placeholder.
  - Editor: paste and drop insert the token, reject a bad type or size, remove the token on upload failure.
  - ImageStore: concurrent get shares one request; lock revokes blob URLs.
  - The failure box.
  - Search and chunk text exclude the `inked://` target.
- **mcp:**
  - `add_image` absent without `image.create`.
  - SSRF: private, loopback and link-local addresses refused, including via DNS and via redirect; rebinding blocked by IP pinning.
  - `path` outside `imageDirs` refused, symlink escape refused.
  - Non-image bytes and over-cap bodies refused.
  - The uploaded blob decrypts in the browser code path.
- **E2E:** the database holds no plaintext image bytes (extends the ciphertext-only check).

### Docs

- `docs/architecture.md`: ciphertext table row; threat-model line on what the server learns; note that `INKED_IMAGE_QUOTA_MB` exists.
- `docs/mcp.md`: the `add_image` tool, `image.create`, `imageDirs`, the URL note.
- `docs/deploy.md`: the database grows with images, so size backups and disk accordingly; the env var.

## Out of scope (v1)

Video; browser link import; orphan cleanup and `DELETE`; SVG; recompression or downscaling; cross-vault references; a file-picker button; sharing a vault between users (vaults are owned by one user today, so there is nothing to share).

## Risks accepted

- The server sees how many images a vault has and how big they are.
- Rollback and replay, as for notes (see the architecture threat model): a malicious server could serve an older or substituted blob for a slot it controls. It cannot forge content for another slot.
- Anything in the page's JavaScript context, if compromised, can read decrypted images, as it can read notes.
